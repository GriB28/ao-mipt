# Архитектура сайта Аэрокосмической олимпиады МФТИ

Документ описывает, как устроен проект: из чего состоит, почему выбран такой стек,
как данные связаны между собой и как это эксплуатировать.

---

## 1. Что должен уметь сайт

| Блок | Что нужно |
|---|---|
| Аккаунты | Регистрация школьников, вход, восстановление пароля, подтверждение e-mail |
| Роли | Участник, организатор (ведёт площадку и проверяет решения), администратор |
| Очный тур | Карта площадок, запись участника на площадку, заявка организатора на новую площадку + модерация |
| Дистанционный этап | Публикация задач по расписанию, загрузка решений файлами, дедлайны, проверка и баллы |
| Контент | Лекции текущего сезона, архив лекций, архив задач с решениями, новости, статические страницы |
| Результаты | Таблица результатов этапа, личный кабинет с баллами, списки для дипломов |
| Рассылки | Письма участникам с выбором аудитории, из админки |
| Админка | Организаторы работают через веб-интерфейс, не через базу и не через Excel |

**Масштаб**: до тысячи участников за сезон, дистанционный этап длится
несколько месяцев, проверка решений ручная. Это снимает целый класс задач —
очереди, кеширование, горизонтальное масштабирование здесь не нужны.
Узкое место проекта не производительность, а время людей: сколько кликов
делает администратор и сколько решений успевают посмотреть проверяющие.

---

## 2. Выбор стека: Django, а не FastAPI

**Рекомендация: Django 5 + PostgreSQL + серверный рендеринг (Django Templates + HTMX).**

FastAPI — отличный фреймворк, но он про API. Здесь 90% работы — это формы, страницы,
загрузка файлов, права доступа и панель управления контентом. Сравнение по задачам проекта:

| Задача | Django | FastAPI |
|---|---|---|
| Регистрация, логин, сброс пароля, хеширование | из коробки | пишем сами (~500 строк + безопасность на нас) |
| Панель управления для организаторов | `django-admin`, генерируется из моделей | пишем сами или клеим SQLAdmin |
| Права и роли | группы + permissions из коробки | пишем сами |
| Миграции БД | встроены (`makemigrations`) | отдельно Alembic, настраивать руками |
| Формы + валидация + CSRF + защита от XSS | встроено | Pydantic только для API, CSRF нет |
| Загрузка файлов | `FileField` + storage backends | пишем сами |
| Поиск человека в команду / примеры на русском | очень много | заметно меньше на такие задачи |

Практический вывод: на Django рабочая версия с регистрацией и админкой появляется
за дни, на FastAPI — за недели, и весь «скучный» код (аутентификация, права,
CSRF, загрузка файлов) придётся написать и защитить самостоятельно. Для сайта,
где регистрируются несовершеннолетние и хранятся персональные данные, это существенный риск.

Опыт с FastAPI не пропадает: Django REST Framework и async-view пишутся похоже,
а Python и ORM-мышление переносятся напрямую.

### Что ещё в стеке

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | знаком команде |
| Фреймворк | Django 5.x LTS-линия | см. выше |
| БД | PostgreSQL 16 (prod), SQLite (локально) | Postgres — стандарт; SQLite чтобы коллега стартовал без Docker |
| Шаблоны | Django Templates + HTMX + немного Alpine.js | не нужен отдельный фронтенд-проект и сборка; SEO работает сам |
| CSS | обычный CSS с переменными (дизайн-токены сезона) | цвет сезона меняется ежегодно — держим в одном файле |
| Карта | Leaflet + OpenStreetMap | бесплатно, без ключей и лимитов; геокодинг адресов — Nominatim, при необходимости заменяется на Яндекс.Геокодер |
| Файлы | локальный диск (старт) → S3-совместимое хранилище | решения участников и PDF задач; см. §7 |
| Почта | SMTP + фоновые задачи | подтверждение регистрации, уведомления о дедлайнах |
| Фон | Celery + Redis (подключается, когда появится нагрузка) | рассылки не должны блокировать запрос |
| Запуск | Docker Compose: gunicorn + nginx + postgres | одинаково на любом хостинге, легко переносить |

**Чего сознательно НЕ делаем:** SPA на React/Vue, отдельный API-бэкенд,
Kubernetes, микросервисы. Это удвоит объём кода при нулевой пользе для
олимпиады на несколько тысяч человек.

## 3. Модули (Django-приложения)

Код разложен по `apps/`, каждое приложение — одна предметная область:

```
apps/
├── core/           базовые модели, главная страница, общие шаблоны и утилиты
├── accounts/       User (вход по e-mail), профиль школьника, роли
├── seasons/        Season (сезон/год), Stage (этап), schedule.py (даты сезона)
├── venues/         Venue — площадка очного тура, модерация, карта, география
├── participation/  Registration — участие в сезоне, запись на площадку
├── contest/        Problem, Submission, Grade — задачи, решения, проверка, результаты
└── content/        Lecture, News, Page, ArchiveItem — лекции, новости, статика, архив
```

Правило зависимостей (чтобы не получить клубок): стрелка = «знает о».

```
        content ──┐
     participation ──┬──> seasons ──> core
        contest   ──┤
         venues   ──┘
            all   ──> accounts
```

`seasons` и `accounts` не импортируют ничего из прикладных модулей. Это позволяет
позже вынести или переписать любой из верхних модулей, не трогая фундамент.

## 4. Модель данных

### 4.1 Сезонность — ключевое решение

Каждый год олимпиада повторяется: новые задачи, новые площадки, те же участники.
Поэтому **почти всё привязано к `Season`**, а не свалено в одну кучу. Это даёт:

* архив прошлых лет бесплатно (`/archive/2025/` — это тот же код с другим сезоном);
* возможность готовить следующий сезон, пока идёт текущий (`is_published=False`);
* отсутствие ежегодной миграции «а давайте заведём новые таблицы».

```
Season (АО VII, 2026/27, active)
 ├── Stage «Дистанционный отбор»  (open_at, deadline, тип=ONLINE)
 │     └── Problem × N ── Submission × M ── Grade
 ├── Stage «Очный финал»          (date, тип=OFFLINE)
 │     └── VenueSlot: площадки, принимающие финал
 ├── Lecture × N
 └── Registration × K (участники этого сезона)
```

### 4.2 Пользователи и роли

```
User (AbstractUser, логин = e-mail)
 ├── role: PARTICIPANT | ORGANIZER | ADMIN
 ├── email_confirmed     — подтверждена ли почта ссылкой из письма
 ├── ParticipantProfile  (ФИО, класс, школа, город, регион из списка,
 │                        телефон или Telegram — хотя бы одно,
 │                        согласие на обработку ПД, дата согласия)
 └── членство в Venue    (для организаторов — какие площадки ведёт)
```

Решения по ролям:

* Роль — поле на `User` + синхронизация с Django-группами. Группы дают готовые
  права в админке, поле `role` — быстрые проверки в шаблонах и view.
* Проверяющий и организатор — один и тот же человек, поэтому доступ к площадке
  определяется связью `Venue.managers`, а не только полем `role`.
* **Персональные данные несовершеннолетних**: хранится минимум, есть явная
  галочка согласия с датой и версией текста согласия, в админке ФИО и телефоны
  видны только ролям с правом. Экспорт списков — с логированием кто и когда выгрузил.

### 4.3 Очный тур и площадки

```
Venue (школа/площадка)
 ├── название, адрес, город, регион
 ├── lat / lon          — координаты для карты
 ├── status             — DRAFT → PENDING → APPROVED / REJECTED
 ├── managers           — организаторы этой площадки (M2M на User)
 └── contact_*          — телефон/почта ответственного
```

Сценарий организатора: регистрируется → жмёт «Заявить площадку» → заполняет форму,
ставит точку на карте → заявка уходит в статус `PENDING` → администратор
одобряет в админке → площадка появляется на публичной карте.

Сценарий участника: открывает карту → выбирает ближайшую площадку → жмёт
«Записаться» → создаётся `VenueBooking`. Запись одна на этап: выбор другой
площадки переносит её, а не добавляет вторую. Ограничения по числу мест нет —
если на площадку запишется больше, чем помещается, организаторы
договариваются вручную.

Карта отдаётся как **GeoJSON-эндпоинт** `/offline/venues.geojson`. Рисует её
Яндекс.Карты, если в `.env` задан `YANDEX_MAPS_API_KEY`, иначе Leaflet поверх
OpenStreetMap. Данные для обоих движков одни и те же.

### 4.3.1 Схема сезона

```
Отборочный тур
 ├── первый уровень — можно участвовать в одном или обоих:
 │    ├── Очный этап            19–24 октября   /offline/
 │    └── Дистанционный этап    15 ноя — 15 янв /online/
 │           │
 │           ▼  по результатам приглашаем дальше
 └── Второй тур                 14 и 28 февраля /second/
        с прокторингом на exams.mipt.ru (Stage.platform_url)
            │
            ▼
Финал                           8–12 апреля     /final/
        кампус МФТИ (Stage.place)
```

Очный и дистанционный этапы — **один уровень отбора**, а не два разных
тура: в модели их связывает общее поле `Stage.order`. Участвовать можно
в обоих, засчитывается лучший результат.

Схема на главной (`templates/components/olympiad_scheme.html`) строится
из этих же записей: названия, даты и место берутся из базы, вёрстка их не
дублирует. Иконку, ссылку и группу задаёт словарь `SCHEME` в
`apps/core/views.py` — отдельной модели под четыре статических элемента
нет намеренно.

Даты лежат в `apps/seasons/schedule.py` и оттуда попадают в базу командой
`seed_demo`; после запуска сезона правятся в админке.

### 4.4 Дистанционный этап

```
Problem
 ├── stage                — к какому туру относится
 ├── status               — DRAFT → PENDING → APPROVED / REJECTED
 ├── created_by, reviewers — автор и назначенные проверяющие
 ├── figure               — рисунок к условию
 ├── title, order, max_score
 ├── statement_pdf     — PDF из LaTeX (основной формат, как сейчас)
 ├── statement_html    — опционально, текст на странице
 ├── attachments       — данные к задаче (signal.txt, csv, картинки)
 └── publish_at        — задача появляется по расписанию

Submission (одна попытка сдачи)
 ├── user, problem
 ├── files             — PDF с решением и/или .py, несколько файлов
 ├── comment           — текст от участника
 ├── created_at        — ставится сервером, сверяется с дедлайном
 └── is_latest         — зачитывается последняя попытка

Grade
 ├── submission, reviewer (организатор)
 ├── score, comment     — что именно снято
 └── status: NEW → IN_REVIEW → GRADED

Score (балл за задачу, независимо от способа сдачи)
 ├── registration, problem
 ├── points             — пусто: не сдавал или не проверено
 ├── venue              — где писал; пусто — дистанционно
 └── entered_by         — кто внёс
```

Зачем `Score` отдельно от `Grade`: на очной площадке участник ничего не
загружает — он пишет на бумаге, и организатор вносит баллы в ведомость.
`Grade` привязан к загруженному решению и для этого не годится. `Score`
описывает результат одинаково для обоих случаев, и итоговая таблица
строится по нему.

Участник видит баллы не сразу, а когда администратор поднимет флаг
`Stage.results_published`: пока ведомости заполняются, недоделанные
результаты утекать не должны.

Это напрямую заменяет нынешний процесс «скачать архив решений → проверить →
забить баллы в `otbor_task8_res.xlsx`»: у проверяющего появляется очередь
(«показать непроверенные по задаче 8»), баллы сразу в базе, выгрузка в Excel
остаётся как кнопка, а не как источник истины.

Автопроверку задач по программированию сюда встроить можно (запуск кода в
изолированном контейнере), но это отдельный крупный кусок — см. дорожную карту.
На первый сезон закладываем ручную проверку + при необходимости сверку ответа
с эталоном для задач с числовым ответом.

### 4.5 Контент

```
Lecture     — название, лектор, дата, видео (YouTube/VK), слайды, сезон
News        — анонсы на главной
Page        — статические страницы (о олимпиаде, правила, контакты) с редактором
ArchiveItem — задачи прошлых лет: сезон, трек, PDF условия, PDF разбора
```

Архив задач и архив лекций — это фильтр по `season` над теми же моделями,
отдельных таблиц не нужно.

## 6. Как работать вдвоём с коллегой

1. **Git с первого дня.** Репозиторий на GitHub/GitLab, `main` защищён,
   работа через ветки и pull request. Никаких правок на сервере.
2. **Окружение поднимается одной командой.** `make dev` (venv + SQLite) или
   `make up` (Docker + Postgres). Если запуск занимает больше 5 минут — это баг.
3. **Секреты не в git.** Есть `.env.example` со всеми переменными и пустыми
   значениями; реальный `.env` — только локально и на сервере.
4. **Фикстуры с демо-данными.** `make seed` создаёт тестовый сезон, задачи,
   площадки и пользователей всех ролей — коллега видит рабочий сайт сразу.
5. **Единый стиль.** `ruff` + `ruff format` в pre-commit, чтобы не спорить о запятых.
6. **Тесты на критичное.** Дедлайны, запись на площадки, права доступа —
   минимум эти три вещи должны быть покрыты, они ломают олимпиаду сильнее всего.
7. **Разделение работы.** Естественная граница: один делает `contest` + `jury`
   (проверка решений), второй — `venues` + `participation` (карта, регистрация).
   Модули почти не пересекаются.

## 7. Хостинг и эксплуатация

### Конфигурация сервера

```
             ┌──────────────── VPS ─────────────────┐
  интернет ──┤ nginx  ──> gunicorn (Django, 3 воркера) │
     :443    │   │                   │                 │
             │   │                   └──> PostgreSQL   │
             │   └──> /static/ /media/ (отдаёт сам)    │
             │        Redis + Celery (рассылки)        │
             └─────────────────────────────────────────┘
```

* **Где размещать.** Российский VPS: Timeweb Cloud, Selectel, reg.ru, Beget.
  Стартовая конфигурация 2 vCPU / 4 ГБ RAM / 40 ГБ SSD (~500–900 ₽/мес) выдержит
  несколько тысяч участников. Альтернатива — инфраструктура МФТИ, если её дадут:
  тогда Docker Compose переносится без изменений.
* **Домен.** Нужен свой (`.ru`, ~200–1000 ₽/год), TLS — Let's Encrypt через certbot, бесплатно.
* **Почта.** Не отправлять письма напрямую с VPS — попадут в спам. Нужен SMTP-релей:
  Яндекс 360 для бизнеса, Unisender, SendPulse.
* **Деплой.** GitHub Actions: при пуше в `main` собирается образ → на сервере
  `make deploy` на сервере (git pull + пересборка; миграции применяются при старте контейнера).
* **Бэкапы (обязательно).** `pg_dump` по cron ежедневно + медиа (решения участников!)
  в объектное хранилище. Раз в сезон — проверка восстановления на тестовом сервере.
  Потеря решений в день дедлайна — самый дорогой сценарий отказа.
* **Мониторинг.** Sentry (бесплатного тарифа хватит) на ошибки + UptimeRobot на доступность.
* **Пиковая нагрузка.** Она предсказуема: последние часы перед дедлайном.
  Перед этим днём — поднять число воркеров и убедиться, что диск не кончается от загрузок.

### Что критично не забыть

* `DEBUG=False` и заполненный `ALLOWED_HOSTS` в проде.
* Лимит на размер загружаемого файла (и в Django, и в nginx) — иначе один
  человек зальёт 2 ГБ видео вместо решения.
* Проверка расширений загружаемых файлов, отдача `media` с `Content-Disposition:
  attachment`, чтобы залитый HTML не исполнился в домене сайта.
* Политика обработки персональных данных на сайте — требование 152-ФЗ,
  раз регистрируются школьники.
