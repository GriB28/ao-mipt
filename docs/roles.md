# Роли, доступы и настройка сайта

Два вопроса, на которые отвечает этот документ:

1. Что видит и может делать каждая роль.
2. **Что настраивается через интерфейс, а что требует правки кода.**

---

## 1. Роли

Ролей три. Роль хранится полем `User.role` и видна в админке
(Пользователи → роль).

| Роль | Кто это | Как появляется |
|---|---|---|
| **Участник** | школьник | сам регистрируется на `/accounts/signup/` |
| **Организатор** | свой человек: ведёт площадку и/или проверяет решения | заводит администратор в админке |
| **Администратор** | вы и коллега | создаётся командой `createsuperuser` |

Отдельной роли «жюри» нет намеренно: площадку ведёт и решения проверяет
один и тот же круг людей. Кто именно что может, задаётся правами Django
(флаг `is_staff` и группы), а не ещё одной ролью — иначе пришлось бы
держать людей сразу в двух ролях и постоянно объяснять разницу.

### Важный принцип: роль сама по себе не даёт прав

Самостоятельной регистрации организаторов нет — это свои люди, их заводит
администратор (см. [admin-guide.md](admin-guide.md), раздел 2). Организатору
достаточно почты и ФИО.

Даже с ролью `ORGANIZER` человек ограничен:

* видит только те площадки, где он указан в поле `Venue.managers`;
* площадка попадает на карту только после одобрения администратором;
* в админку `/admin/` не попадает — для этого нужен флаг `is_staff`,
  который выдаёт только администратор;
* обычный участник страницу добавления площадки открыть не может вовсе.

То же с проверкой решений: пока администратор не поставит `is_staff` и не
добавит в группу «Проверяющие», организатор не увидит чужих решений.
Это покрыто тестами (`apps/accounts/tests.py::OrganizerAccessTest`).

### Что делает каждая роль

**Участник**
- регистрируется, заполняет анкету, подтверждает почту;
- видит задачи дистанционного этапа после их публикации;
- загружает решения до дедлайна, может перезаливать — зачтётся последняя версия;
- выбирает площадку очного тура на карте и записывается;
- после публикации результатов видит свои баллы и комментарии проверяющих.

**Организатор**
- заводит задачи и отправляет их на одобрение администратору;
- добавляет площадку: адрес, точка на карте, контакты;
- правит свою площадку, включая описание для участников;
- ведёт ведомость своей площадки: список записавшихся и баллы по задачам;
- пишет письма участникам своей площадки;
- после одобрения видит в кабинете, сколько человек к нему записалось;
- не видит участников чужих площадок;
- если добавлен в группу «Проверяющие» — открывает очередь непроверенных
  решений, скачивает файлы, ставит балл и пишет комментарий;
- не может менять задачи, сроки и пользователей.

**Администратор**
- всё вышеперечисленное плюс: сезоны и этапы, публикация задач, модерация
  площадок, назначение ролей, рассылки, редактирование страниц сайта.

### Как дать человеку доступ к проверке решений — по шагам

1. Админка → Пользователи → выбрать → поле **роль** = «Организатор».
2. Поставить галочку **Статус персонала** (`is_staff`) — без неё админка закрыта.
3. Вкладка **Группы** → добавить в группу «Проверяющие».
4. Группу «Проверяющие» нужно создать один раз: Админка → Группы → Добавить,
   права: `contest | решение | Can view submission`, `contest | оценка |
   Can add/change/view grade`. Больше ничего не давать.

Шаг 4 делается один раз за всё время жизни проекта.

## 2. Что настраивается в интерфейсе, а что в коде

Это главная развилка: если что-то меняется каждый сезон, это должно
настраиваться кликами. Если это меняется раз в жизни — пусть живёт в коде.

### ✅ Через админку, без программиста

| Что | Где в админке |
|---|---|
| Создать новый сезон, сделать его активным | Сезоны → Сезоны |
| Цвет и логотип сезона | Сезоны → Сезон → «цвет сезона», «логотип» |
| Этапы, даты начала и **дедлайны** | Сезоны → Этапы |
| Открыть и закрыть запись на очный тур | Этап → «запись открывается/закрывается» |
| Добавить задачу и материалы к ней | сайт: «Дистанционный тур» → «Добавить задачу»; материалы — Задачи → Задачи |
| Время открытия задач (общее для этапа) | Сезоны → Этапы → «начало» |
| Выложить разбор после этапа | Задача → «разбор», «разбор доступен с» |
| Одобрить или отклонить площадку | Площадки → действие «Одобрить» |
| Завести организатора | Пользователи → Добавить, роль «Организатор» |
| Одобрить задачу, назначить проверяющих | Задачи → действие «Одобрить», поле «дополнительные проверяющие» |
| Опубликовать баллы участникам | Очный тур → ведомость площадки → «Опубликовать результаты» |
| Порядок этапов и схема на главной | Сезоны → Этапы: «порядок», «формат», «подпись на схеме» |
| Плейлисты лекций на YouTube и ВК | Контент → Плейлисты |
| Фотографии финалов | Контент → Фотографии |
| Одобрить лекцию | Контент → Лекции → действие «Одобрить» |
| Тексты страниц «Второй тур» и «Финал» | Сезоны → Этапы → «описание» |
| Даты и подписи на схеме главной | Сезоны → Этапы: «даты на схеме», «место проведения» |
| Записать участника на площадку вручную | Участие → Записи на площадки |
| Назначить роль, заблокировать пользователя | Пользователи |
| Проверить решение, поставить балл | Задачи → Решения |
| Новости, лекции, статические страницы | Контент |
| **Текст правил и согласия на обработку ПД** | Контент → Страницы |
| **Рассылка участникам** | Рассылки → создать → кнопка «Отправить рассылку» |

Практический вывод: **весь ежегодный цикл олимпиады проходит без единой
строчки кода.** Новый сезон, новые задачи, новые даты, новые площадки —
это работа администратора в браузере.

### 🎨 Через один файл, без программиста

| Что | Где |
|---|---|
| Вся палитра, шрифты, отступы, скругления | `static/css/tokens.css` |

Это файл для дизайнера. Подробности — в [design.md](design.md).

### ⚙️ Требует правки кода

| Что | Почему так |
|---|---|
| Новое поле в анкете участника | меняется структура базы — нужна миграция |
| Список регионов в анкете | один файл `apps/accounts/regions.py`, миграция не нужна |
| Деление задач на направления или классы | сознательно убрано: комплект задач общий |
| Новый тип этапа (например, «командный тур») | новая логика, а не новая запись |
| Автопроверка задач по программированию | отдельная подсистема |
| Изменение правил подсчёта результатов | бизнес-логика |
| Новый раздел сайта (например, «Партнёры») | новый шаблон и маршрут |
| Интеграция с Telegram-ботом | новый код |

Правило на будущее: **если вы ловите себя на мысли «придётся просить
программиста каждый сезон» — это ошибка проектирования, и настройку нужно
вынести в админку.** Сейчас таких мест нет.

## 3. Почты, пароли и база данных

Короткий ответ: **отдельной базы паролей заводить не нужно, Django делает
это сам, и делает правильно.**

### Где всё хранится

Одна база PostgreSQL (локально — файл SQLite). Таблица `accounts_user`:

| Поле | Что внутри |
|---|---|
| `email` | логин, приведённый к нижнему регистру, уникальный |
| `password` | **не пароль**, а его хеш |
| `role` | роль |
| `email_confirmed` | подтверждена ли почта |
| `is_active` | можно ли войти |

### Как устроены пароли

Пароль **никогда не хранится и не может быть восстановлен** — ни вами, ни
администратором, ни при утечке базы. Хранится результат алгоритма PBKDF2:
320 000 повторов хеширования со случайной «солью» у каждого пользователя.

Что это значит на практике:

* при входе сравниваются хеши, а не пароли;
* забытый пароль нельзя «посмотреть» — только сбросить по ссылке из письма
  (маршруты уже настроены: `/accounts/password-reset/`);
* если база утечёт, подобрать пароли будет крайне дорого;
* Django сам проверяет пароль на длину (минимум 8), на совпадение с почтой
  и на попадание в список 20 000 самых частых паролей.

Менять здесь ничего не нужно и не стоит: самописная криптография — самый
частый способ всё сломать.

### Вход по почте, а не по логину

`USERNAME_FIELD = "email"`, поле `username` удалено. Регистр не важен:
`Ivan@Mail.ru` и `ivan@mail.ru` — один и тот же человек (см.
`apps/accounts/backends.py`). Почта уникальна, два аккаунта на один адрес
завести нельзя.

### Отправка писем

Сайт **не хранит** почтовые пароли в коде — они берутся из `.env`
(`EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`), который не попадает в git.

Письма уходят через внешний SMTP-релей, а не напрямую с сервера — иначе
почти всё попадёт в спам. Локально письма не отправляются, а печатаются в
консоль, так что тестировать можно без настройки почты вообще.

Типы писем:

1. подтверждение адреса при регистрации *(в планах, задача 1 дорожной карты)*;
2. восстановление пароля *(работает)*;
3. рассылки администратора *(работает, см. ниже)*.

### Рассылки

Админка → Рассылки → Добавить. Указываете тему, текст и аудиторию:

* все зарегистрированные участники;
* участники конкретного сезона;
* **сдавшие хотя бы одну задачу** / **зарегистрированные, но ничего не сдавшие**;
* записавшиеся на очный тур;
* организаторы.

Дальше кнопка **«Отправить рассылку»** на странице рассылки. Открывается
подтверждение: сколько человек получит письмо, первые десять адресов и
предпросмотр текста. Случайно разослать тысяче школьников нельзя.

В тексте можно писать `{{ first_name }}` и `{{ last_name }}` — подставится имя
получателя.

Три вещи, сделанные намеренно:

* **Письма уходят по одному, каждому на свой адрес.** Ни копий, ни скрытых
  копий: адреса школьников не должны видеть друг друга.
* **Отправка идёт в фоне, порциями.** Тысяча писем — это несколько минут;
  если слать их прямо по кнопке, браузер отвалится, а половина писем уйдёт
  дважды при повторном нажатии.
* **Повторный запуск ничего не дублирует.** У каждого письма своя запись в
  базе; если отправка упала на 500-м, она продолжится с 501-го.

На сервере очередь разбирает контейнер `mailer` (он поднимается вместе
с сайтом, см. [deploy.md](deploy.md)) — отдельный cron не нужен.

Кому письмо не дошло и почему — видно в админке: Рассылки → Письма.

## 4. Согласие на обработку персональных данных

Галочка при регистрации теперь ссылается на два документа:

* `/page/consent/` — согласие на обработку данных;
* `/page/privacy/` — политика обработки данных.

Оба созданы как обычные страницы и **редактируются в админке** (Контент →
Страницы). Сейчас там заготовки с пометкой «ЧЕРНОВИК» и местами для
заполнения в квадратных скобках.

**Эти тексты обязательно должен вычитать юрист МФТИ до открытия
регистрации** — вы собираете данные несовершеннолетних, требования к этому
строже обычных. Что именно нужно уточнить — в [152fz.md](152fz.md).

При регистрации в базу пишется не только факт согласия, но и дата с версией
текста (`consent_version`). Если вы поменяете текст согласия, поднимите
`CONSENT_VERSION` в `apps/accounts/forms.py` — тогда будет видно, кто
соглашался на старую редакцию, а кто на новую.
